# XMagital面试防御清单

> 面试官质疑不是敌意，是在测试细节掌握。核心原则：不回避，承认边界，用具体细节托底。

## 一、质疑数字
### 召回率从 63% 到 77% 怎么来的？
这是在 30 个工业场景查询上测的。我手动标注 Ground Truth，然后看系统 Top-5 里是否包含正确答案。单路向量检索命中 19/30，三路混合检索命中 23/30。测试集不大，所以我不会说这是生产长期指标，只说在这批测试问题上方向有效。

### 23ms 响应时间怎么来的？
这是在测试图谱上测的。N+1 版本每步 DFS 都查数据库，中位数约 176ms；优化后一次性加载 nodes 和 edges 到内存，再在内存里 DFS，中位数约 23ms。生产环境边数更多，加载可能更慢，如果到百万级需要换增量加载或 Neo4j。

### 54% Token 节省靠谱吗？
这是 20 段工业文档上的对比测试。三次调用约 3200 tokens/段；三合一单次成功约 1350 tokens/段，考虑约 15% 的重试率后约 1600 tokens/段。实际节省在 50%-58% 之间，对外说约 54%，比理想值保守。

## 二、质疑是否是你做的
### 这些不都是 AI 生成的代码吗？
AI 负责的是写代码这个机械工作，我负责判断 AI 写得是否正确。

具体例子：
1. 分块：AI 一开始只用一次 Parent-Child 分块，我测出三元组完整率不理想，判断需要两阶段分块。
2. RRF：AI 第一版用原始分数加权，我发现三路分数量纲不统一，改成排名融合。
3. 图谱：反向根因候选追溯最初沿用了顺向那套 BFS + 永久 visited，我用菱形图测出候选漏报，把反向候选链路改成 DFS + 路径级 visited 回溯；顺向因果链和方案路径仍然是 BFS。如果追问“怎么保留每条独立路径”，答案是 `enumerateRootCausePaths`。
4. 熔断器：AI 用 setTimeout，我发现进程重启后会死锁，改成时间戳按需检查。

我没有从零敲每一行代码，但关键设计决策、测试验证和纠错是我做的。

### 这个项目是你一个人做的吗？
不是。知识库子系统由三人协同开发，我负责三条核心链路：知识注册流水线、混合检索问答、知识图谱根因分析。分区管理、设备术语审核、图谱边审核、平台级用户认证由两位同事负责。前端和其他子系统由公司团队其他同事负责。

### 你说主导，具体主导了什么？
主导的是我负责链路里的关键技术判断和落地：两阶段分块、三合一抽取、三路检索、RRF 融合、DFS 回溯、N+1 查询优化、时间戳熔断、本地 ONNX 降级等。团队整体架构和边界是一起讨论确定的。

### 一个实习生能做完这么多吗？
首先这不是整个系统由我一个人做，而是三人协同开发。其次三条链路是按数据流顺序逐步做的：先知识注册，再检索，再图谱根因分析；熔断和降级是贯穿全程逐步加固。最后，我大量使用 AI 辅助编码，时间主要花在方案设计、测试验证和纠正 AI 的错误方案上。

## 三、质疑技术理解
### DFS 回溯为什么能避免漏路径？
用菱形图举例：同一个根因可能通过两条不同路径导致同一个故障。如果 visited 永久保留，第一条路径访问过共享节点后，第二条路径到这个节点会被截断。DFS 回溯是在当前路径返回时删除 visited，使同一节点可以出现在另一条合法路径里。

补充一句边界（诚实口径）：遍历层面两条路径都会被走到，但 `findRootCauseCandidates` 末尾按 `node_id|hop_count` 去重，所以菱形图里同跳数到达同一根因的两条路径最终只保留置信度最高的一条候选。要保留每条独立路径，走 `enumerateRootCausePaths`（不去重），它的输出才用于 Noisy-Or 证据聚合。

### 那 BFS 还在用吗？为什么不统一成 DFS？
还在用，而且是刻意保留的。两种遍历目标不同：

- 顺向的因果链构建和方案路径搜索要回答「这个故障会影响到哪些节点」，关心的是可达集合和跳数分层，永久 visited 去重正好避免重复展开，所以用 BFS（`buildCausalChain` / `findSolutionPaths`）。
- 反向根因候选追溯要回答「这个现象可能来自哪些候选根因」，用 DFS + 路径级 visited 枚举后按 `node_id|hop_count` 去重（`findRootCauseCandidates`）。
- 「从这个现象往上有哪几条独立因果路径」是另一个函数的职责：`enumerateRootCausePaths`，它复用同样的反向 DFS 语义但不做去重，输出供 Noisy-Or 证据聚合。

如果顺向也改成 DFS 逐条枚举路径，在稠密图上路径数会指数膨胀，而顺向场景只需要可达集合、并不需要区分路径，纯属浪费。所以这不是「哪个更好」，是按查询语义选遍历方式。

### RRF 和直接加分有什么区别？
直接加分要求三路分数同量纲，但向量相似度、pg_trgm 相似度、精确匹配固定分并不在同一量纲。RRF 不看绝对分数，只看各路排名，把排名折算为 1/(k+rank)，避免被分数量纲绑架。

### 熔断器为什么用时间戳而不是 setTimeout？
核心原因是进程重启死锁。setTimeout 存在内存里，服务在熔断打开期间重启后定时器丢失，熔断器可能永远停在 open。时间戳记录打开时刻，每次请求进来按需判断是否超过恢复窗口，不依赖定时器，也避免 Timer 泄漏和事件循环阻塞导致的状态切换延迟。

## 四、质疑技术选型
### 为什么不用 Elasticsearch？
Elasticsearch 全文检索能力更强，但需要独立部署、JVM 调优、备份和运维。我们的知识规模是万级，pg_trgm 查询延迟够用，并且和 PostgreSQL/pgvector 在同一数据库内，避免双写一致性问题。百万级复杂检索再考虑 ES。

### 为什么不用 Milvus？
Milvus 需要 etcd、MinIO 等组件，工厂内网运维成本较高。项目规模在万级知识点，pgvector 一个 PostgreSQL 扩展就够，同时事务一致性更简单。

### 为什么不用 Neo4j？
Neo4j 适合十万到百万级复杂图查询。但本项目图谱规模在万级以内，PostgreSQL 全量加载到内存后 DFS 性能足够，还避免引入新的数据库和双写一致性问题。

### BGE-M3 为什么合适？
text-embedding-ada-002 只有 API 版，不能本地部署；m3e-base、bge-large-zh 上下文较短，工业规程段落容易截断；BGE-M3 支持长文本且中英混合表现更适合设备型号场景。没有做同等测试集的向量质量定量对比，这是可承认的边界。

## 五、质疑项目价值
### 这个系统真的上线了吗？
这是实习期间的校企合作项目，我负责的三条链路在测试环境端到端跑通，接口已对接团队其他模块。代码交付给公司后，我没有权限跟踪生产部署情况，所以不声称已经生产运行。

### 类似 RAG 开源项目很多，你这个有什么不同？
通用 RAG 多是单路向量检索 + LLM 生成。本项目针对工业场景做了三点适配：设备型号/编号精确匹配，知识图谱根因分析，工厂内网离线部署和降级。它不是完美生产级产品，但体现了针对工业场景的工程判断。

## 六、实战被驳回过的质疑（真实面试验证）

> 完整护城河话术见 [[护城河与不可替代性]]。

### 换个懂这套技术栈的人也能做吧？
❌ 已被驳回：难点在结合业务做决策、按文档类型分别处理、SDD 方法论、人主导 AI 执行。
被驳原因：这些换任何同行都能一字不改说出来，等于自认没有护城河。

✅ 承认 + 重构：先承认技术栈通用，再把稀缺性重新定义为「知道哪里会踩坑并用测试证伪过」，然后甩三个反直觉修正（单路检索→三路 RRF、BFS→DFS 回溯、一刀切分块→两阶段）。
判断标准：一句话如果同行都能照说，就是废话，必须往下钻到具体 bug 和数字。

### 知识库怎么嵌入研发流程？
❌ 已被驳回：只讲「能查资料」，显得是孤立的问答工具。

✅ 映射到研发五个节点：立项调研查历史与标准、设计阶段查规范与选型、调试故障用根因分析追溯（价值最大）、测试验收比对标准并生成报告初稿、归档复盘把新经验重新注册形成闭环。
落地按三步走体现不冒进：先被动查询 → 再在固定节点主动推送清单 → 最后做带人工确认的流程编排。关键是嵌进对方现有流程，不要求对方改习惯。

### 文档变多后 176ms→23ms 会不会退化？
❌ 不能硬说不会退化，也不能临场编（第一场就是临场编的）。

✅ 诚实承认 + 证明知道拐点：会有影响，但退化的是加载环节不是 DFS 本身。详细分层路径见 [[XMagital项目数据口径]] 的「性能拐点与扩展路径」。
落点：当前方案在当前数据量下是合适解，规模上去有明确分层降级路径，不做提前过度设计。

### 大模型和人工怎么分工？你了解到什么程度？
❌ 已被驳回：只讲「人主导、AI 执行」的原则，显空。

✅ 用一个具体 bug 定位过程证明钻进过代码：让 AI 把 BFS 改成 DFS 回溯后**仍然**漏路径，因为它漏掉了回溯时 `delete visited` 这一步；是用菱形测试图跑出第二条路径找不到才定位到的，再让它改第二次。

⭐ `delete visited` 是最硬的「真做过」证据——它是「AI 改了一版还是错、我又测出来」的二阶细节，编不出来。任何「是不是你做的」质疑都可以甩它。

### 向量检索用什么模型？
送分题但要带选型理由：BGE-M3，1024 维，本地 ONNX 推理。三个理由——支持 8192 token 长段落、有开源 ONNX 版可本地离线跑（数据不出域，涉密内网硬要求）、本地 CPU 单条 40-60ms 精度与开销平衡。远程 API 只作降级。

### 有没有可演示的系统？
❌ 第一场没拿出来，一次性坐实了「换个人也能做」和「是不是你真做的」两个质疑。

✅ 随身带脱敏截图：问答 + 溯源标注、根因图谱 + 置信度、四层架构图、知识图谱总览。一张真实界面胜过十句「我真做了」。
