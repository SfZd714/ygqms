# 军工横向项目文档开发与规范问答

> 本页用于支撑 自我介绍与核心竞争力 中“参与研究所合作项目申报、软件文档、内部开发与部署”的追问。
> 它讲的是军工/科研院所横向软件项目中常见的文档协同方法和本人已确认参与的工作类型，不把未核实的单位模板、标准编号、评审结论或本人主笔范围写成事实。
>
> 与 [[横向军工项目面试介绍]] 的关系：前者聚焦项目和技术模块；本页聚焦文档链路、规范意识、评审整改和保密边界。

## 一、先记住自己的角色边界

推荐说法：

> 我参与的是本子系统相关材料的编写和维护，不是项目总负责人，也不是所有文档的唯一作者。通常由项目负责人统一组织目录、版本和提交，系统/模块负责人提供技术内容，我根据分工完成本子系统的功能、接口、测试和使用说明，并根据评审意见修改和回归确认。

不要说：

- 独立完成整套军工项目材料；
- 主导项目立项、合同、经费或总体验收；
- 掌握所有涉密技术细节；
- 参与过但实际没有接触的标准编号、质量体系或审查流程。

## 二、文档之间的关系

可以用“从目标到交付”的链路解释：

```text
项目申报书
  → 软件需求规格说明书
  → 软件设计说明书
  → 编码与联调
  → 配置项测试报告
  → 用户手册 / 部署说明
  → 专家逐项验收与问题整改
  → 工作总结报告 / 汇报材料
```

这不是说所有项目都严格按这一条线性顺序完成，而是说明不同文档服务于不同阶段。实际项目往往边开发边补充文档、边评审边修订，需要保持前后一致。

## 三、各类文档怎么写、关注什么

### 1. 项目申报书

**作用**：说明为什么做、做什么、怎么做、达到什么目标以及如何组织实施，服务于立项论证和项目评审。

**本人可采用的参与表述**：

> 我主要提供本子系统的建设内容、功能边界、技术路线、数据流和阶段性成果描述，配合项目负责人把模块目标、输入输出和验证方式写清楚。

**写作注意**：

- 项目目标、建设内容、技术路线和验收方式要互相对应；
- 不把“计划支持”写成“已经实现”；
- 指标必须有测试口径和责任边界；
- 总体目标与本人模块目标分开写；
- 涉密内容使用项目允许的脱敏层级，不在普通材料中扩散。

### 2. 软件需求规格说明书

**作用**：把项目目标转成可开发、可测试、可验收的软件需求。

**一个需求点至少要能回答**：

- 谁使用、在什么条件下使用；
- 输入数据是什么，来源和格式是什么；
- 系统执行什么处理；
- 输出什么结果，字段和状态如何定义；
- 异常输入、失败和边界情况如何处理；
- 如何验证该需求已经实现。

**本人模块可用表达**：

> 对监控防御子系统，我参与把多源流量、日志和告警数据的输入，以及攻击识别、告警生成和前端展示的输出整理成具体功能点，保证后续设计和测试能够逐项对应。

**常见问题**：

- 需求描述只有“实现智能检测”，没有输入、输出和验收条件；
- “实时”“准确”“高可靠”等词没有定义口径；
- 一个功能点混入多个不可独立验证的目标；
- 需求书写了自动防御，但实际只完成检测告警；
- 字段名称、枚举值和页面名称前后不一致。

### 3. 软件设计说明书

**作用**：说明需求如何落地为系统结构、模块、接口、数据处理和异常处理。

**本人模块应重点交代**：

- 模块边界和与数据资源池、前端、其他子系统的关系；
- 输入数据如何进入检测流程；
- 五类攻击检测和告警输出的处理链路；
- Flask 接口与前端展示的职责分工；
- 消息传递、失败处理和日志记录；
- 关键字段、数据流和状态转换；
- 如何支持测试、联调和无网环境使用。

**稳妥表述**：

> 设计说明书不是把代码逐行翻译成文字，而是让评审人员、开发人员、测试人员和后续维护人员能够理解模块边界、接口约束、处理流程和异常路径。我的工作重点是整理本子系统实际承担的功能与接口，并保持设计、实现和测试之间的一致性。

### 4. 软件配置项测试报告

**作用**：记录配置项或功能点是否按照需求实现，形成可复核的测试证据。

**一个测试项建议包含**：

| 内容 | 说明 |
|---|---|
| 测试编号 | 与需求/功能点建立对应关系 |
| 测试环境 | 版本、运行环境和必要配置，按可公开范围描述 |
| 前置条件 | 数据、服务和依赖是否准备完成 |
| 输入/步骤 | 测试人员实际执行的操作和数据 |
| 预期结果 | 应出现的识别、告警、接口或页面结果 |
| 实际结果 | 实际观察到的结果 |
| 结论 | 通过、未通过或需整改 |
| 证据 | 日志、截图、输出文件或记录，按保密要求管理 |

**五类攻击测试的通用组织方式**：

- 每类攻击至少有正常样例、命中样例和边界/异常样例；
- 验证数据是否正确进入检测链路；
- 验证检测结果字段和告警类型是否正确；
- 验证前端是否能展示关键结果；
- 验证重复告警、空数据、格式异常和服务异常时的表现；
- 测试实际结果必须如实记录，不能为了“通过”而修改预期或隐瞒问题。

> ❓具体测试编号、样例数量、指标和最终通过结论待确认，当前不写入网申或面试数字。

### 5. 用户手册

**作用**：让目标用户能够按步骤使用系统，而不要求用户阅读源代码或设计文档。

**建议内容**：

1. 系统用途和适用范围；
2. 登录/启动/进入功能页面的前置条件；
3. 数据导入或数据接入说明；
4. 攻击检测和告警查看步骤；
5. 查询、筛选、详情和结果解释；
6. 常见异常及处理建议；
7. 不能做什么，以及需要人工确认的环节；

**注意**：用户手册和软件实际界面必须一致。专家现场按手册操作时，任何按钮名称、字段名称、启动步骤或截图过时，都会直接影响验收可信度。

### 6. 工作总结报告

**作用**：总结完成的工作、阶段成果、问题整改、交付情况和后续工作。

**推荐结构**：

- 项目任务与本人承担范围；
- 已完成的功能和文档；
- 测试、联调和部署情况；
- 评审或验收中发现的问题及整改；
- 当前限制和未完成事项；
- 后续改进计划。

不要把“原型验证通过”写成“长期生产运行”，也不要把团队成果全部写成个人成果。

### 7. 项目汇报 PPT

**作用**：面向评审或验收人员，用有限篇幅讲清项目目标、系统结构、完成情况和验证证据。

**本子系统建议顺序**：

1. 子系统在总体架构中的位置；
2. 数据来源和检测对象；
3. 五类攻击检测与告警功能；
4. 前后端和消息链路的功能边界；
5. 测试与联调结果；
6. 问题整改和当前交付状态。

PPT 只放可公开、可验证、与本次汇报相关的内容；不使用涉密截图、真实地址、真实拓扑和内部数据。

## 四、文档一致性检查清单

提交或评审前，可按以下顺序自查：

- [ ] 项目名称、版本、日期和文档状态一致；
- [ ] 本人负责范围与团队分工一致；
- [ ] 需求中的每个功能点都能在设计、实现和测试中找到对应；
- [ ] 设计中的输入、输出、字段和页面名称与实际一致；
- [ ] 测试预期结果来自需求，不临时修改成实际结果；
- [ ] 用户手册按当前版本实际操作过；
- [ ] PPT 结论能由测试记录或交付材料支撑；
- [ ] 缺陷、限制和未完成内容有记录，不用模糊词掩盖；
- [ ] 文件版本、审批/评审状态和修改记录可追溯；
- [ ] 截图、日志、样例数据和附件按保密等级管理；
- [ ] 普通工作材料不包含项目代号、型号、拓扑、真实地址和内部指标。

## 五、评审和验收时怎么回答

### Q：你在文档中具体写了哪些内容？

> 我主要负责本子系统相关内容：项目申报书中的建设内容和技术路线，需求说明中的功能边界、输入输出和验收条件，设计说明中的数据流、处理流程和接口关系，用户手册中的功能操作说明，以及配置项测试报告中的测试步骤、预期结果和实际结果。总体目录、版本统筹和最终提交由项目负责人组织，我按分工提供和维护模块材料。

### Q：申报书、需求书和设计书有什么区别？

> 申报书回答“为什么建设、建设什么、总体怎么实施”；需求规格说明书回答“软件必须提供什么能力，以及怎样判断满足要求”；设计说明书回答“这些需求在系统中如何实现，包括模块、接口、数据流和异常处理”。三者不是重复改写，而是从项目论证逐步细化到可开发、可测试的工程内容。

### Q：如何保证文档和代码一致？

> 我会以需求功能点为索引，核对设计中的模块和接口，再用测试项验证实际行为；如果评审或联调发现页面、字段或流程和文档不一致，就先判断是实现问题还是文档过期，再同步修改并回归验证。重点是形成“需求—设计—实现—测试—手册”的对应关系。

### Q：专家指出文档和系统不一致，你怎么处理？

> 先记录具体差异和对应功能点，不急于判断责任；再确认当前实际行为、需求原文和设计说明，判断需要改代码、改文档还是两者都改。修改后重新执行对应测试，并同步更新用户手册或汇报材料，避免只改现场展示而没有留下闭环记录。

### Q：军工项目文档和普通互联网项目文档有什么不同？

> 我理解主要差异不只是文档更多，而是更强调需求可追溯、过程可审查、版本可管理、测试有证据、交付可复现和保密边界清晰。互联网项目也需要质量控制，但军工或研究所项目通常更重视正式评审、配置项管理、验收功能点和文档与实物的一致性。

### Q：你知道哪些具体军工软件标准？

> 我参与项目时重点是按项目组确定的模板、流程和评审要求完成本子系统材料。具体标准编号、适用版本和单位内部细则需要以项目正式下发文件为准，我不凭记忆引用未经确认的标准编号。可以确认的是，我实际接触过需求、设计、用户手册、配置项测试、评审整改和无网联调这些工作环节。

### Q：涉密材料如何管理？

> 首先按项目规定确定材料密级、知悉范围和流转方式；其次只在授权环境和授权人员范围内处理，不把真实数据、拓扑、型号和内部截图带到非授权环境；再次做好版本、修改和交接记录；对外交流只讲经过允许的概括性内容。遇到不确定的信息，先向项目负责人或保密管理人员确认，不自行判断“应该没关系”。

### Q：你能把项目材料带出来展示吗？

> 涉密或商业敏感材料不能带出。面试中可以介绍脱敏后的工作类型和通用技术方法；如果准备演示，只使用经过确认的脱敏架构图或重新制作的无敏感示意图，不使用真实地址、真实网络拓扑、内部截图和项目指标。

### Q：无网环境下文档要特别注意什么？

> 需要提前确认安装包、依赖、模型或规则文件、配置文件、测试数据和操作手册是否能在授权环境内闭环使用；部署步骤要能按手册复现；服务启动顺序、端口、目录和数据导入方式要与实际环境一致。现场遇到问题要记录环境、步骤、日志和处理结果，不能依赖临时联网或现场口头经验。

### Q：你参与的是写文档，会不会只是整理文字？

> 文档工作不是脱离开发的文字整理。需求文档要能指导设计和测试，设计文档要能反映真实模块和接口，测试报告要有实际证据，用户手册要能指导操作。我参与文档时需要回到功能、数据流、接口和测试结果核对内容，因此也能帮助发现需求、实现和交付之间的不一致。

## 六、面试表达红线

| 不要说 | 改成 |
|---|---|
| 我主导了整个军工项目文档 | 我参与本子系统相关文档编写和维护 |
| 我负责项目申报和验收 | 我参与申报材料编写、评审和功能点验收配合 |
| 按军工标准严格完成 | 按项目组确定的模板、流程和评审要求完成 |
| 做了自动防御闭环 | 负责范围主要是检测、告警和展示 |
| 已经上线运行 | 原型功能完成测试/联调，具体生产状态不作延伸 |
| 所有材料都能展示 | 只能介绍经确认可公开的脱敏内容 |
