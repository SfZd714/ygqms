# XMagital项目叙事脚本

> 用于回答「介绍一下你的项目」。不要只堆技术名词，要讲成亲历的开发故事。保持第一人称：「我测试发现」「我判断」「我改成」。

## 一句话串起整个项目
我在和利时实习，团队做了一个工业知识库系统。我负责后端三条核心链路：文档怎么变成知识入库、用户问问题怎么检索出答案、设备报警怎么追溯到根因。

## 30秒版
XMagital 是面向工业场景的企业知识库系统。工业文档里很多内容是设备故障、原因和处理步骤，通用大模型没有这些私有知识，传统 RAG 固定切片又容易切断因果链。我在知识库子系统中负责知识注册、混合检索和图谱推理三条后端核心链路。项目里我做了两阶段分块、三合一抽取、三路混合检索、RRF 融合、BFS 顺向因果链 + DFS 回溯反向根因追溯和本地 ONNX 降级等设计，重点是让系统查得准、能溯源、离线也可用。

## 2分钟版
我在和利时实习期间参与 XMagital 工业知识库系统。这个项目解决的是工业领域通用大模型缺乏企业私有设备知识的问题，比如设备故障原因、操作规程、维修步骤都在企业内部文档里，模型如果直接回答容易泛化甚至编造。

我负责知识库子系统后端三条核心链路。第一是知识注册流水线：我测试发现简单固定切片会破坏工业文档里的「现象—原因—处理建议」因果链，所以采用两阶段分块，先保留章节语义供 LLM 抽取，再切成适合检索的小块入库；同时用三合一 LLM 抽取替代三次调用，Token 消耗从约 3200/段降到约 1600/段。

第二是 RAG 混合检索：单路向量检索在设备型号、编号这种精确查询上容易混淆，我设计了向量、关键词、精确匹配三路并行，用 RRF 做排名融合，再用 LLM Reranker 精排。在 30 个测试问题上，Recall@5 从 19/30 提升到 23/30。

第三是知识图谱推理：顺向的因果链构建和方案路径搜索用 BFS 分层扩散，但反向根因候选追溯我用菱形图谱测出永久 visited 会漏掉共享中间节点的多条路径，所以反向候选链路单独实现为 DFS + 路径级 visited 回溯；如果要保留每条独立路径，则用 `enumerateRootCausePaths` 做路径枚举；同时把每步查数据库的 N+1 查询改为一次性加载内存后遍历，响应从约 176ms 降到约 23ms。

这个项目给我的最大收获是：AI 生成代码可以提高效率，但关键是要用测试验证方案是否正确，再做工程判断。

## 模块1：知识注册流水线
### 核心故事
项目初期，直接按固定长度切块会把故障处理步骤切断，LLM 看到的可能只是「第2步：更换轴承」，却不知道这是哪个故障的处理步骤，导致三元组抽取残缺。我判断「喂给 LLM 的块」和「存数据库检索的块」目标不同，不能共用一个切块函数，于是拆成两阶段分块：大块保证语义完整，小块保证检索粒度。

### 追问要点
- 标题模式：Markdown 标题、中文章节号、数字层级、附录等。
- 三合一抽取：实体、三元组、关系一次生成，减少重复输入 Token。
- 结构校验：zod 校验 + 实体引用检查，失败重试。

## 模块2：RAG 混合检索
### 核心故事
单路向量检索对语义问题有效，但工业场景有很多型号编号查询，向量会把相近型号混淆。我测试后加了三路：pgvector 处理语义，pg_trgm 处理关键词，ILIKE 精确匹配处理型号编号。融合时不用原始分数加权，因为三路分数不在同一量纲，改用 RRF 看排名。

### 追问要点
- RRF 不看绝对分数，只看各路排名。
- k=60 是 RRF 常用默认参数。
- Reranker Top-20 是成本和效果折中。
- Reranker 失败时降级返回 RRF 原始顺序，不中断主链路。

## 模块3：知识图谱根因分析
### 核心故事
图谱推理里两种遍历都在用，分工不同。顺向的因果链构建和方案路径搜索用 BFS，按跳数分层扩散拿影响面，永久 visited 去重就够。但反向根因候选追溯目标不同——它要找到候选根因，不一定保留每条路径，所以我先用 DFS + 路径级 visited 枚举，再在函数末尾按 `node_id|hop_count` 去重；如果追问“那怎么保留每条独立路径”，答案是走 `enumerateRootCausePaths`。

### 追问要点
- 顺向因果链与方案路径：BFS + 永久 visited（`buildCausalChain` / `findSolutionPaths`）。
- 反向根因候选追溯：DFS + 路径级 visited 回溯（`findRootCauseCandidates`）；如果要保留每条独立路径，用 `enumerateRootCausePaths`。
- 两者不是替换关系，是按遍历目标分工：BFS 求「影响到哪些节点」，DFS 求「候选根因或独立证据路径」。
- 深度惩罚：超过 3 跳后每多一跳衰减，过滤深层噪声。
- 矛盾检测只标记，不自动修改，保留人工审核。

## 模块4：离线部署与嵌入降级
### 核心故事
工厂内网不能假设远程 API 永远可用。我设计本地 BGE-M3 ONNX 优先，失败或超负载再切远程 API，远程连续失败后打开熔断器快速失败。熔断器不用 setTimeout，而用时间戳按需判断，避免进程重启后定时器丢失导致永远 open 的死锁问题。

### 追问要点
- 本地 ONNX：约 40-60ms/条，离线可用。
- 远程 API：约 200-400ms，受网络影响。
- 熔断器三态：Closed → Open → Half-Open。
- 熔断在外、重试在内，统计的是重试耗尽后的最终失败。

## 团队分工标准表述
不是我一个人做的。知识库子系统由三人协同开发，我负责知识注册流水线、混合检索问答、知识图谱根因分析三条核心链路。分区管理、设备术语审核、图谱边审核和平台级用户认证由两位同事负责。我们按模块分工、接口对齐后各自实现。
