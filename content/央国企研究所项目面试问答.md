# 央国企研究所项目面试问答

> 适用于国防科研院所、军工央企、央国企研究院及信息化部门。回答时以 [XMagital项目叙事脚本](XMagital项目叙事脚本.html) 为主项目，以 [千言·AI智能助手后端系统](千言·AI智能助手后端系统.html) 补充 Java 后端能力，以研究所合作经历证明对文档、流程和保密边界的适应性。
>
> 使用原则：先给结论，再讲本人动作，最后用结果或反思收束。没有确认的数据不补；没有参与的模块不揽；涉密项目不讲代号、指标、单位全称和业务细节。

## 一、面试官总体在看什么

这组问题表面在问项目，实际通常同时考察：

1. **真实性**：项目是不是本人做的，能否说清职责边界和实现细节；
2. **工程能力**：能否把目标拆成模块并推进到可测试、可交付；
3. **问题解决能力**：面对难点是否有判断、验证、取舍和闭环；
4. **技术深度**：是否理解技术为什么这样选，而非只会罗列名词；
5. **迁移能力**：已有经验能否迁移到型号、科研生产和信息化场景；
6. **协作与规范**：是否能按接口、流程、文档和质量要求协同；
7. **稳定性与动机**：是否真正理解单位和岗位，而非只追逐热点。

## 二、回答项目问题的通用结构

建议采用“五句法”：

1. **项目是什么**：业务对象与核心痛点；
2. **我负责什么**：角色和明确边界；
3. **我怎么做**：关键技术动作和选择理由；
4. **结果如何**：测试数据、性能或交付状态；
5. **我学到了什么**：工程判断、协作或规范意识。

不要从技术栈开始背，也不要连续讲五分钟等面试官打断。

## 2. 该项目的核心目标是什么？你是如何推进并达成目标的？

### 考察意图

- 是否具有目标拆解、计划推进和结果验证能力；
- 是否能把技术动作与业务价值对应起来。

### XMagital 主答版

> 项目的核心目标，是让企业内部工业文档和设备经验真正能够被检索、引用和用于故障分析，而不是让大模型凭通用知识直接作答。围绕这个目标，我把自己负责的工作按数据流拆成三步推进：先解决知识“进得来”，完成文档解析、标题感知分块和结构化抽取；再解决知识“查得准”，用向量、关键词和精确匹配三路检索配合 RRF 与重排序；最后解决故障知识“能追溯”，通过知识图谱构建因果链和根因候选路径。每一步都先建立小规模测试集验证，再根据结果调整方案。最终在 30 个工业问题测试中，Recall@5 从 19/30 提升到 23/30；图谱查询也通过消除 N+1 查询把测试响应从约 176ms 降到约 23ms。我的推进方式不是先堆功能，而是按主链路逐段打通、测试、再加固。

> 千言项目的目标是用 Java 原生方式完成一套可对外提供服务的 AI Agent 后端，把模型调用、RAG、会话管理、工具调用、安全和监控放在同一套 Spring Boot 工程内。我先搭建分层后端和 REST/SSE 接口，再依次实现 Redis 会话、ParadeDB 混合检索、工具与 MCP、安全护轨，最后补充监控、评测和 Docker 配置。推进时按“接口可调用—数据可持久化—效果可评测—运行可观察”的顺序迭代。

- 知识能否进入系统；
- 查询能否准确召回；
- 答案能否溯源；
- 系统能否在受限环境稳定运行。

## 3. 项目执行过程中遇到的最大难点是什么？你是如何解决的？

### 考察意图

- 是否真的经历过问题，而不是复述项目介绍；
- 能否定位根因、比较方案并通过测试闭环；
- 遇到困难时是等待指令，还是主动形成解决路径。

### XMagital 首选答法：固定切片破坏因果链

> 最大难点是工业文档不能简单按固定长度切片。文档中“故障现象—原因—处理步骤”往往跨多个段落，固定切片后模型可能只看到某一步操作，却不知道对应哪个故障，导致抽取和检索都不完整。我先用实际文档构造测试样例，确认问题来自同一套切块同时服务抽取和检索，而两者目标不同。之后把流程拆成两阶段：较大的章节块用于保留完整语义并供模型抽取，较小的子块用于数据库检索。这样既保留因果上下文，又控制检索粒度。这个问题让我认识到，数据预处理不能只看通用方案，必须根据业务语义和下游任务分别设计。

### XMagital 备选答法：图谱路径漏报

> 在反向根因追溯中，我用菱形图测试发现，如果直接沿用顺向遍历的 BFS 加永久 visited，共享中间节点会导致第二条有效路径被截断。我重新区分了两类目标：顺向因果链关注按跳数扩散，继续使用 BFS；反向根因候选和独立证据路径需要保留路径上下文，因此采用 DFS 加路径级 visited 回溯，并在候选层按节点和跳数去重。这个修正不是简单换算法，而是先澄清“求影响范围”和“求候选路径”是两个不同问题。

### 千言 Java 后端备选答法：混合检索链路

> Java 项目中的难点是把语义检索和关键词精确检索统一到一条可维护的链路里。单纯向量检索对语义问题有效，但对编号、术语和专有名词不稳定；BM25 又不擅长语义近似。我在 ParadeDB 中并行使用向量检索和 BM25，再用 RRF 按排名融合，最后通过 Rerank 做精排。这样避免直接混加不同量纲的原始分数，同时让检索流程可以分阶段观察和调试。

### 不建议的说法

- “时间紧、任务重，但我加班完成了”；
- “技术太难，我查资料解决了”；
- “最大的困难是沟通”；

这些回答没有问题诊断与技术动作，区分度很低。

## 16. 请详细介绍最有代表性的一个项目

### 考察意图

### 参考回答：XMagital

>
> 我的推进顺序是先让知识进得来，再让知识查得准，最后让故障关系能够追溯。知识入库阶段采用标题层级感知分块；检索阶段采用向量、关键词和精确匹配三路召回，再通过 RRF 和重排序融合；图谱阶段区分顺向 BFS 因果链与反向 DFS 路径回溯。
>
> 项目中一个代表性问题是固定切片破坏故障因果链。我通过真实文档测试确认原因后，将抽取和检索拆成不同粒度：较大章节块保留完整语义，较小子块服务检索。另一个问题是反向追溯沿用永久 visited 会漏掉菱形结构中的第二条路径，我通过构造菱形图用例发现问题，改成路径级 visited 回溯。最终 Recall@5 在 30 个问题测试中从 19/30 提升到 23/30；图谱测试响应从约 176ms 降到约 23ms。
>
> 这个项目让我形成的核心能力不是只会调用模型，而是能够从业务语义、数据处理、检索、算法、测试和可靠性几个层面做工程闭环。

## 17. 讲讲你项目的架构

### 考察意图

判断你是否真正理解系统边界、数据流、模块职责、部署与异常路径，而不是只负责局部编码。

### XMagital 架构回答

> 我负责的知识库子系统可以按数据流分为五层。第一是接入与解析层，负责多格式文档解析和标题层级感知分块；第二是知识注册层，进行实体关系抽取、切块和批量持久化；第三是检索层，使用向量、关键词和精确匹配三路并行召回，通过 RRF 和重排序生成上下文；第四是知识图谱层，支持顺向因果链、解决方案路径和反向根因候选追溯；第五是可靠性与隔离层，包括多租户分区过滤、本地 ONNX 嵌入、远程 API 降级、熔断和重试。
>
> 查询链路是：用户问题进入后先携带分区信息，三路检索并行召回并融合，候选片段交给模型组织答案，同时保留来源切片；故障追溯类问题则进入图谱遍历链路。系统设计的重点是私有知识可检索、答案可溯源、不同租户隔离，以及外部模型不可用时仍有降级路径。

### 千言 Java 项目架构回答

> 千言后端采用标准分层结构：Controller 层提供 REST 和 SSE 接口；Service 层组织会话、RAG、Agent 和知识库业务；AI 核心层通过 LangChain4j 管理模型、聊天记忆、Tool、Skill 和 Guardrail；存储层使用 Redis 保存会话记忆，ParadeDB/PostgreSQL 保存文档元数据、切块和向量，本地 Markdown 保存知识原文；监控层使用 Actuator 和 Micrometer 采集调用次数、Token、耗时与错误指标。主链路是请求进入、读取会话、检索与精排、组装上下文、模型判断是否调用工具、输出 JSON 或 SSE，同时记录指标和异常。

## 31. 举一个成功解决复杂问题的例子

### 考察能力

- 判断能否把 AI 转化为实际效率，而非追逐概念。

### 参考回答

> 我平时会把 AI 当作辅助分析、编码和复盘工具，而不是把它当成最终决策者。在开发中，我会用它辅助梳理需求、生成初步方案、补充测试用例、解释陌生 API 和检查边界情况；但生成代码必须经过我自己的规格约束、代码审阅、运行测试和结果核对。XMagital 中固定切片破坏因果链、检索分数不能直接加权、图谱反向遍历会漏路径等问题，都是我通过测试发现并修正的，并不是直接接受 AI 的第一版答案。
>
> 在学习中，我会让 AI 帮助整理知识点、比较方案和模拟追问，再回到官方文档、代码和实验结果核验。使用 AI 时尤其注意数据边界：不把涉密资料、未公开业务信息、个人敏感信息和公司内部代码直接输入外部模型；研究所或军工环境中应优先使用经过批准的本地化工具，并遵守单位保密规定。
>
> 我的原则是“AI 提高分析和实现效率，但技术判断、数据安全和最终结果责任仍由本人承担”。

### 结合岗位的收束句

> 对信息化项目而言，我更关注 AI 能否在合规前提下提高文档整理、知识检索、测试辅助和问题定位效率，而不是为了使用 AI 而使用 AI。

## 40. 你对企业 KPI 有什么看法？

### 考察意图

- 判断目标意识、组织适应性和责任心；
- 了解你是否能接受考核和过程管理；
- 观察你是否只重视个人技术兴趣，不重视交付结果；
- 考察能否平衡数量、质量、风险和长期价值。

### 参考回答

> 我认为 KPI 或阶段目标本质上是把组织目标转化为可执行、可检查的工作要求，我可以接受并愿意对自己的目标负责。对软件和信息化项目来说，不能只看功能数量或代码量，还应该结合交付质量、测试覆盖、问题闭环、文档完整性、系统稳定性和协作效果来评价。比如检索系统如果只追求上线速度，却忽略召回准确性、数据隔离和异常降级，短期指标可能完成了，但长期会增加维护和业务风险。
>
> 我的做法是先确认目标、范围、验收标准和优先级，再把任务拆成阶段里程碑；执行中及时同步风险，必要时说明资源和时间约束；交付后用测试数据、问题记录和文档证明结果。如果进度和质量发生冲突，我会尽早暴露问题，与负责人确认取舍，而不是临近节点才隐瞒风险或为了指标牺牲底线。
>
> 在军工和信息化场景中，我理解考核还应体现规范、可靠性、保密和可追溯性。我的态度不是排斥 KPI，而是希望在明确目标的基础上，用正确的方法完成任务，同时守住质量和安全底线。

### 追问：如果 KPI 与技术判断冲突怎么办？

> 我会先确认冲突的具体性质：如果是范围、时间和实现方案的取舍，就把不同方案的成本、风险和影响量化后请负责人决策；如果涉及数据安全、保密、质量红线或虚假填报，则不能为了完成指标绕过底线，应按流程上报并保留记录。能交付是目标，合规、质量和真实是前提。
